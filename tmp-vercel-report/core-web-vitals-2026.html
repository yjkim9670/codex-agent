웹 성능은 더 이상 “몇 초 만에 뜨는가”만의 문제가 아니다. 사용자가 누르고, 기다리고, 화면이 흔들리지 않는 경험까지—세 개의 Core Web Vitals가 현대 웹의 체감 품질을 정의한다.
Google Core Web Vitals공식 문서 기준Single File HTML

빠른 웹사이트라는 말은 오랫동안 로딩 속도를 뜻했다. 하지만 실제 사용자는 로딩이 끝난 뒤에도 계속 판단한다. 버튼이 즉시 반응하는지, 클릭 후 화면이 멈추지 않는지, 읽던 문장이 이미지 때문에 밀리지 않는지. 오늘의 성능 평가는 ‘보이는 속도’에서 ‘상호작용의 질’로 넓어졌다.

Good 기준. Google은 페이지뷰의 75번째 백분위수에서 세 지표를 평가하도록 권장한다. 막대는 각 지표의 poor 경계 대비 good 기준의 상대 위치를 나타낸다.

LCP는 “언제 핵심이 보였는가”, INP는 “눌렀을 때 얼마나 빨리 다음 상태가 그려졌는가”, CLS는 “화면이 얼마나 안정적으로 머물렀는가”를 묻는다. 이 셋을 함께 보면 페이지가 빠른지뿐 아니라 사용 과정이 신뢰할 만한지까지 평가할 수 있다.

좋은 성능은 단순히 빨리 뜨는 페이지가 아니라, 사용자의 다음 행동을 방해하지 않는 페이지다.

왜 INP가 중요한가

INP는 한 번의 클릭만 재는 지표가 아니다. 방문 중 발생한 상호작용을 관찰하고 전반적인 반응성을 대표하는 값을 잡는다. 초기 화면이 빠르게 뜨더라도 메인 스레드가 긴 JavaScript 작업으로 막혀 있다면 버튼, 메뉴, 입력창은 둔하게 느껴진다.

느린 상호작용의 전형적 경로사용자 입력 → 메인 스레드 대기 → 이벤트 핸들러 → 스타일·레이아웃 → 페인트. 어느 단계가 길어져도 사용자는 “눌렀는데 안 먹힌다”고 느낀다.
01

입력 지연 줄이기. 긴 태스크를 쪼개고 메인 스레드를 독점하는 JavaScript를 줄인다.

02

핸들러 가볍게 만들기. 즉시 필요한 상태 업데이트를 먼저 처리한다.

03

다음 페인트를 빨리 허용하기. 무거운 후속 작업은 가능한 한 뒤로 미룬다.

04

필드 데이터로 확인하기. 실험실 점수만이 아니라 실제 사용자 분포의 75번째 백분위수를 본다.

숫자를 목표가 아니라 경계로 읽기

Google은 임계값을 인간 지각 연구와 실제 웹에서의 달성 가능성을 함께 고려해 정했다고 설명한다. INP 역시 지각 관점에서는 더 짧을수록 좋지만 실제 모바일 환경의 달성 가능성을 함께 고려해 200ms가 good 경계로 정해졌다.

그래서 좋은 설계는 “200ms만 넘지 않으면 된다”가 아니라, 자주 수행하는 핵심 상호작용에서 가능한 한 빠른 시각적 피드백을 주고 낮은 성능의 장치에서도 무너지지 않는 방향이어야 한다.

디자인과 성능은 같은 문제다

성능을 엔지니어링의 마지막 최적화 단계로만 보면 놓치는 것이 많다. 레이아웃 이동은 이미지 크기 예약 실패에서, 버튼 지연은 과도한 인터랙션 로직에서, 느린 LCP는 무거운 대표 자산 선택에서 시작될 수 있다. 편집, UI 설계, 자산 전략과 실행 성능은 처음부터 연결돼 있다.

콘텐츠형 웹 실무 체크첫 화면의 대표 콘텐츠를 명확히 하고, 이미지 크기를 사전에 확보하며, 초기 JavaScript를 최소화한다. 메뉴·필터·아코디언처럼 자주 누르는 조작은 시각적 피드백을 먼저 주고 무거운 후속 작업을 뒤로 미룬다.
